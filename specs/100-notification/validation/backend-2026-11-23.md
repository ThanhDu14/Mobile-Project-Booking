## Implemented behavior

- Server helper validates canonical type/identity/recipient, persists exactly the existing six inbox fields, and prepares inbox/job writes during the source transaction's read phase. Existing UUID inbox writers retain their IDs. Job IDs hash the approved tuple. Existing inbox is never backfilled with a new job after retention. Existing source transition guards prevent UUID replay after terminal job cleanup.
- W1 adapters: owner booking decisions, booking timeout, waitlist promotion/closure, application approval/rejection and SYSTEM. Waitlist callbacks after commit were removed from cancel/dropin-close/owner-update-session to avoid duplicate creation. Legacy waitlist without a ticket keeps an active recipient's inbox without inventing a delivery identity.
- Worker: authenticated cron endpoint, FCM HTTP v1 data-only sender, per-token attempt reservation/receipt, two-minute fenced lease, crash recovery, partial success, six-attempt retry policy, Retry-After, exact UNREGISTERED cleanup and seven-day terminal retention. Target initialization pages 100 receipts, freezes targets once, fails explicitly over budget. Each invocation allows at most 50 claims/50 FCM requests with a 90-second processing budget. Retention drains at most 100 child receipts/job/visit before parent deletion. Account deletion blocks new enqueue/initialization via profile reads, drains receipt children before parents and repeats in final sweep.
- Token coordinator uses the existing profile array, a transaction without an offline mutation queue, UID/epoch guards and device-only UID/hash/rotation metadata excluded from backup. It rotates before a new UID registers, preserves other devices and reuses successful rotation during failed-registration retries to avoid an onNewToken feedback loop. Existing FcmSignOutHook pauses registration through a lazy core interface before its existing best-effort removal/delete; no second removal hook or server device registry was introduced. OS denial detaches the known token hash; grant/resume/network/new-token can retry. SDK/local failures do not block inbox/preferences.
- C1 presence is scoped to installation, with the existing 60-second/45-second client lease cadence. Leaving one installation only deletes its lease. Server push checks any live lease and muted separately; inbox recipients are no longer filtered by those conditions in the legacy chat callback. Participant removal, purge and account anonymization drain presence children. **Chat callback transport/durable message enqueue remains unimplemented**, so this is not completion of CHAT_MESSAGE delivery.
- P1 Android service accepts exactly recipientUid/notificationId, rejects foreign/unknown sessions and notification-block messages, obeys OS permission and renders generic PRIVATE/public content. Immutable tap intents load own inbox by ID from SERVER, including items outside the first page, then reuse the current access-checking resolver and saved-detail fallback. No arbitrary source URI is accepted from FCM.
- Channel setup is idempotent and preserves existing user/channel settings. No runtime grant or notification post occurs while creating it. BOOKING_NEW remains forced eligible and PROMOTION defaults off; disabling any other type does not prevent inbox persistence.
