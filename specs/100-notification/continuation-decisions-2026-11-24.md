## D3: DROPIN_REGISTERED, existing request identity

Source: register-drop-in/handler.ts, register() already validates a UUID requestId and replays the current registration without a new write. joinWaitlist() and addParty() are separate commands. Proposed event key: family dropin-registration, identity JSON([sessionId, userId, requestId, "DROPIN_REGISTERED"]), deterministic n_{jobId}; source recipient is authenticated registrant. Call shared prepareNotification during the existing transaction read phase and append its writes to the source writes. Remove the post-commit callback only for this event. Data {sessionId}, title "Đăng ký buổi chơi thành công", body "Mở vé để xem thông tin buổi chơi." All six inbox fields and existing delivery schema unchanged.

Business choice requiring approval: retain the explicit DROPIN_REGISTERED confirmation already emitted by Feature 080, as an exception to the generic no-self-action wording. No notification for joining/leaving waitlist, adding party, or cancelling one's registration. Waitlist promotion/closure retain approved D2-W1. For rejoin require a fresh requestId. If a stale request ID's deterministic inbox already exists but the current source registration is no longer that successful attempt, reject the stale command with 409 before source writes; never charge/register a new attempt without its own event. No command journal/collection is added. Missing legacy event history is not backfilled.

Impact: Feature 080 contract, register transaction/callback and tests. Opens remaining REGISTERED tests in T021 and part T023/T025; DROPIN_CHANGED remains outside this approval.

## R1: review create and first reply

Source: review/handler.ts currently creates REVIEW_NEW and canonical REVIEW_REPLIED via callbacks after commit; callback failure is swallowed. Review ID can be reused after delete/recreate, so ID alone is insufficient.

Propose reviews/{id}.notificationGeneration: String UUID generated by server when the review is created. Keep it on edit; a recreated review gets a new UUID. For a legacy review lacking generation, assign one in its first reply transaction without backfilling REVIEW_NEW. Client cannot set/update generation; source server remains authoritative. Event family review; identity JSON([reviewId, generation, canonicalType]). Enqueue REVIEW_NEW for current venue owner, REVIEW_REPLIED for review author only on first owner reply, never on later reply edits. Skip notification to the acting user; keep the business write. Check active/non-deleting recipient and current venue ownership in the source read set. Preserve content/data {reviewId,venueId}, deterministic n_{jobId}; no second callback. Inbox/job share the source transaction. No general HTTP event envelope.

Impact: CSDL review field and Feature 070 contracts/producer, tests delete/recreate/reply replay/rollback/actor exclusion. Opens part T044/T046. REVIEW_REMINDER timing/repetition and OWNER_REVOKED request identity are separate unresolved decisions, not included.

- DROPIN_CHANGED: no durable change-generation/request protocol confirmed for repeated edits/cancellation. Need owner command requestId + retained operation identity and registered-recipient snapshot before implementation. Do not use updatedAt milliseconds as a uniqueness guarantee.
- GROUP_ACTIVITY/group CHAT_MESSAGE: need one durable source fanout snapshot/outbox in source transaction. Proposed next design must state snapshot fields, byte/write budget, recipient pages, cancellation/deletion/access checks, leases/retries and cleanup. Unbounded member fanout cannot be treated as an atomic two-write-per-user loop; no collection/fields are approved here.

- OWNER_REVOKED: propose stable admin requestId and replay lookup before role mutation, so an old request cannot revoke a later reapproval. Requires API/UI and durable replay storage design; not authorized by D2-W1's application review.
- REVIEW_REMINDER: resolve Feature 070 repeat wording versus Feature 100 once, then define eligibility/timing/identity and query. No scheduler marker/schema is approved by R1.

These remain explicit blockers in T004/T005/T013/T018/T022–T025/T035/T044–T048/T056 as applicable. Their draft directions are not implementation contracts.
